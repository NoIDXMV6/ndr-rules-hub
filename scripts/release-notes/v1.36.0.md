Инцидент «контейнер unhealthy, docker logs пусты, рестарт не помогает» — инициализация БД ограничена по времени и стала громкой (v1.36.0).

Причина (диагностика продакшена): db-heal (проверка/докатка схемы БД перед стартом сервера) выполнял ТЯЖЁЛЫЕ операции молча и БЕЗ ограничения времени: полный `PRAGMA integrity_check` на разросшейся БД (после зависших DNS-сборок — миллионы доменных записей и гигабайтный WAL), проверку до 15 снимков подряд (каждый — полный скан), мультигигабайтный `VACUUM INTO`. Всё это — до `exec node server.js`: приложение не стартует, healthcheck не отвечает (`Up N minutes (unhealthy)`), логи контейнера пусты (первый вывод db-heal печатался только ПОСЛЕ завершения проверки), рестарт повторяет зависание — диагностировать невозможно.

db-heal.cjs — каждый тяжёлый шаг под таймаутом и с выводом ДО начала работы:
- Первой строкой лога — размеры `hub.db`, `-wal`, `-shm` и свободное место тома (гигабайтный `-wal` — след зависших сборок), плюс параметры скана и предупреждение, если WAL больше самой БД.
- Ограничение времени на каждый шаг (DB_HEAL_TIMEOUT_MS, по умолчанию 90 с): чтение sqlite_master (включая открытие БД/recovery WAL), скан целостности, проверка каждого снимка, VACUUM INTO, каждый ALTER/CREATE INDEX, wal_checkpoint. По таймауту шаг пропускается с внятным сообщением (stderr) — молчаливых шагов не осталось.
- bounded-скан: `PRAGMA quick_check(25)` (стоп после 25 проблем — быстрый фейл на повреждённой БД) вместо полного `integrity_check`; полный — только вручную через `NDR_DB_FULL_CHECK=1`.
- Дешёвая структурная проверка (страница 1 + sqlite_master) ловит «database disk image is malformed» сразу, без полного скана; ALTER'ы по повреждённой БД запрещены (восстановление из снимка — до докатки).
- Снимков проверяется максимум 5 (было 15), каждый со своим таймаутом.
- Восстановление из снимка корректно переоткрывает БД: у клиента, открытого до подмены файла, кэш страниц старого файла — сверка схемы после restore раньше ломалась («сверка схемы не удалась»).
- Коды выхода: 0 — ок/докатано; 1 — ДОКАЗАННОЕ повреждение без здоровых снимков; 2 — проверка не успела (таймаут) — БД не считается повреждённой.
- flush stdout/stderr перед process.exit: в pipe (docker logs) хвост диагностики раньше обрезался.
- После успешной проверки — `wal_checkpoint(TRUNCATE)`: гигабайтный WAL от зависших сборок подрезается, следующий старт не тратит время на recovery.

docker-entrypoint.sh — рестарт больше не может зависнуть молча:
- Первая строка лога — размеры БД/WAL/SHM и свободное место (том данных видно до любых операций).
- db-heal запускается под глобальным `timeout` (DB_HEAL_TIMEOUT, по умолчанию 300 с, `--kill-after=30`).
- rc=2/124/137 (таймаут) → БД НЕ стирется: сервер стартует с существующей БД, проверка повторится при следующем рестарте, ошибки БД видны в логах и /api/health. Раньше ЛЮБОЙ сбой db-heл приводил к подмене БД шаблоном — на медленном диске с большой БД это делало рестарт бесконечно молчащим или теряло данные. Стирание теперь только при доказанном повреждении (код 1) — с бэкапом, как прежде.

Стартовая диагностика приложения (stdout): одна строка на клиент БД при старте — `[db interactive/heavy] SQLite: journal=wal, БД … MB, freelist N страниц, wal-файл … MB` (src/lib/db.ts) — живость/размер БД видны в `docker logs` без запросов к API.
