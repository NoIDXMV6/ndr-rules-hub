# Дашборды OpenSearch: аналитика и каталог dashboards (v1.14.0)

Раздел хаба «Дашборды OpenSearch» наполняет пустые по умолчанию разделы
OpenSearch Dashboards (OSD) **Alerting**, **Anomaly Detection** и
**Security Analytics** данными Suricata EVE (`logstash-*`) и добавляет
каталог дополнительных дашбордов.

## Почему разделы были пустыми

Плагины alerting / anomaly-detection / security-analytics входят в сборку OSD
3.x и потому видны в меню, но clearNDR не создаёт в них объектов — они пустые
«с завода». Данных для наполнения достаточно: события
`event_type = alert | flow | dns | http | tls | fileinfo` в индексах
`logstash-*`.

## Что создаётся

### Alerting (мониторы, префикс «NDR ·»)

| Монитор | Условие | Interval | Severity |
|---|---|---|---|
| 01 Критический алерт Suricata | `alert.severity=1` > 0 | 5 мин | 1 (Critical) |
| 02 Всплеск алертов severity 2 | > 50 за период | 10 мин | 2 |
| 03 DNS-флуд | `event_type:dns` > 1000 | 5 мин | 3 |
| 04 Активность fileinfo | `event_type:fileinfo` > 0 | 15 мин | 5 (Info) |
| 05 Всплеск сетевых потоков | `event_type:flow` > 5000 | 5 мин | 3 |

Действие каждого монитора — запись в индекс аудита `ndr-alerts-audit`
(работает без SMTP/Slack; webhook можно добавить штатными средствами OSD →
Notifications). Просмотр срабатываний: OSD → Alerting → Monitors → Findings,
а также индекс `ndr-alerts-audit`.

### Anomaly Detection (ML-детекторы)

- «NDR · Аномалии объёма трафика (исходящие байты)» — сумма
  `flow.bytes_toserver` по каждому источнику (категория — src_ip);
- «NDR · Аномалии DNS-запросов по источникам» — число dns-событий по
  каждому источнику.

Интервал детекции 5 мин, окно задержки 2 мин. Первые результаты — через
10–15 минут: OSD → Anomaly Detection → Detector results.

### Security Analytics

Детектор «NDR · Suricata network (Sigma)» типа `network` по `logstash-*` +
маппинг EVE→ECS (`src_ip→source.ip`, `dest_ip→destination.ip`,
`alert.signature→rule.name` и т.д.). Встроенные Sigma-правила network
подключаются плагином автоматически; свои правила — OSD → Security
Analytics → Rules.

## Каталог дашбордов (packs)

| Ключ | Название | Содержимое |
|---|---|---|
| `traffic` | Обзор трафика | metric, динамика событий, pie транспорта, топ источников/портов/протоколов |
| `http` | HTTP | динамика, методы, топ хостов/URL, коды ответа |
| `dns` | DNS | динамика, топ запросов, типы, rcode, источники |
| `tls` | TLS | динамика, топ SNI, JA3-отпечатки, источники |
| `alerts` | Алерты Suricata | динамика по severity, топ сигнатур, категории, источники/цели |
| `files` | Файлы | всего, топ имён, типы (magic), динамика |

Поля в пакетах записаны плейсхолдерами и подставляются при импорте по
фактическим маппингам кластера (`_field_caps`): EVE raw или ECS. Если поля в
кластере нет — соответствующая визуализация пропускается с WARN. Пакеты
идемпотентны (`ndr-pack-*`), штатные дашборды SELKS не затрагиваются.

Перед импортом скрипт сам находит, куда реально поступают EVE-события
(`_cat/indices` + проба `event_type`/`event.type`): index-pattern берёт титул
равный найденному выражению (обычно `logstash-*`). Найденному паттерну
(например, оставшемуся от SELKS) список полей **дополняется из кластера** —
иначе OSD показывает «Could not locate that index-pattern-field» на
`dns.*`/`http.*`/`alert.*`. Для текстовых полей (динамический маппинг)
подставляется keyword-подполе (`proto.keyword` и т.п.) — Terms-агрегации
по text-полю в OSD не работают («Saved field "proto" is invalid for use
with the "Terms" aggregation"). В финале печатается число документов и
время последнего события под паттерном.

## Скрипты

- `scripts/clearndr-osd-analytics-setup.sh` — режимы `--status`,
  `--apply-alerting`, `--apply-anomaly`, `--apply-security`, `--apply-all`,
  `--remove-managed`; опции `--yes`, `--dry-run`, `--instance-dir`,
  `--es-url`, `--seed`, `--webhook`.
- `scripts/clearndr-osd-dashboard-import.sh` — `--check`, `--list`,
  `--pack <key|all>`, `--remove <key|all>`; те же опции соединения. Объекты
  пишутся в `.kibana` сырым форматом SavedObjects (`type`, атрибуты под
  именем типа, `references`, `migrationVersion` — версия берётся с
  существующих объектов кластера); bulk-тело уходит файлом/потоком с
  сохранением завершающего `\n` (bulk API OpenSearch отвергает тело без
  него) и `refresh=wait_for`.
- `scripts/osd-pack-generator.py` — генератор пакетов (пересоздаёт
  `scripts/osd-packs/*.json`).

## Доступ к OpenSearch (автоопределение канала)

Порядок перебора (первый отвечивший кластер используется дальше):

1. **OpenSearch URL** из настроек раздела (вкладка → поле «OpenSearch URL»;
   пусто = авто). Можно с авторизацией: `https://user:pass@host:9200`.
2. `https://127.0.0.1:9200` и `http://127.0.0.1:9200` — режим SSH (скрипт
   выполняется на хосте) или хаб с `--network host`.
3. `https://172.17.0.1:9200` и `http://172.17.0.1:9200` — шлюз docker-моста:
   основной вариант для **local**-режима (хаб в контейнере), работает, если
   9200 опубликован на хосте (`ss -ltnp | grep 9200`).
4. `https://host.docker.internal:9200` (https/http).
5. `docker exec` в контейнер `-opensearch-<seed>` — работает всегда, когда
   контейнеру хаба смонтирован `/var/run/docker.sock` (даже если 9200 не
   опубликован на хосте).

Схема (https/http) определяется автоматически, самоподписанный сертификат
принимается (`curl -k`). Если OpenSearch отвечает `401/403` — в ошибку
добавляется подсказка указать URL с учётными данными. Команда/хост, по
которому OpenSearch найден, показываются в карточке состояния раздела
(«Канал») и выводятся скриптами.

## Режим local: требования к контейнеру хаба

Контейнер хаба на хосте с Clear NDR должен быть запущен с монтированиями:

```sh
docker run … \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /opt/ClearNDR:/opt/ClearNDR \
  ndr-rules-hub
```

- `/var/run/docker.sock` — поиск контейнеров стека, канал `docker exec`,
  статус стека, определение версии OSD;
- каталог инстанса **по тому же пути**, что на хосте (`/opt/ClearNDR`) —
  бэкапы объектов, реконструкция compose, `stamusctl`;
- `docker` CLI, `python3` и `stamusctl` (amd64) уже входят в образ;
- healthUrl должен быть доступен из контейнера (например
  `https://172.17.0.1/`). Если указан публичный домен и он не проксирует
  `/rest/`, probe стека автоматически пробует шлюз `https://172.17.0.1`.

Если монтирований нет, раздел показывает причину (нет docker-сокета / нет
прав / нет docker CLI) и подсказку с готовой командой запуска.

## Резервные копии и удаление

Перед каждой заменой/удалением объект сохраняется в
`/opt/ClearNDR/backups/osd-analytics-<ts>/` (или `osd-import-<ts>/`).

## Из хаба

Вкладка «Дашборды OpenSearch»: карточка состояния (кластер, версии, канал
доступа, плагины, объёмы данных, счётчики управляемых объектов), поле
«OpenSearch URL» для переопределения автоопределения, выбор вида аналитики,
каталог пакетов с чекбоксами, «сухой режим», живой лог прогона и история.
Скрипты выполняются на хосте по той же схеме, что и «Обновление Clear NDR»
(общие настройки соединения; синхронизация скриптов и пакетов — перед
прогоном).

### Управление прогонами: остановка и зависшие прогоны

- Пока идёт прогон, новые запуски заблокированы. Активный прогон показывается
  баннером «Выполняется прогон OSD» с прошедшим временем и кнопкой
  **«Остановить прогон»**; кнопка есть и в строках истории, и в шапке лога.
- Остановка: раннеру отправляется SIGTERM (при упорстве — SIGKILL), в лог
  пишется `[hub] Прогон остановлен пользователем.`, код выхода — 143,
  в истории прогон помечается бейджем «остановлен».
- Зависшие прогоны. Раннер — detached-процесс; если контейнер хаба
  перезапускался, процесс погибал, не записав код выхода, и прогон навсегда
  оставался «выполняется», блокируя новые запуски. Теперь при каждом опросе
  статуса живость процесса проверяется по pid: если процесса нет, а `rc` не
  записан — прогон автоматически помечается остановленным (rc=143, строка
  `[hub] процесс прогона не найден …` в логе), и блокировка снимается. Прогон
  без pid-файла, запущенный более 3 минут назад, помечается так же.
  Это же справедливо для прогонов «Обновления Clear NDR» (update-*).
- Переиспользованный pid. После пересоздания контейнера хаба тот же номер
  pid может достаться чужому процессу: без дополнительной проверки зависший
  прогон считался бы «живым» бесконечно, а «Остановить» убивало бы
  посторонний процесс. Движок сверяет возраст процесса
  (`/proc/<pid>/stat`, поле `starttime`) с возрастом прогона: если процесс
  заметно старше/моложе прогона — pid чужой, прогон помечается остановленным
  без kill (в логе — `[hub] pid принадлежит другому процессу …`).
- Экстренное снятие блокировки вручную (на хосте, если не хочется ждать
  опроса статуса): прогон живёт в томе хаба `<каталог хаба>/data/`
  (`clearndr-osd/runs/<runId>`, для обновлений — `clearndr-update/runs/`):

  ```bash
  echo 143 | sudo tee <каталог хаба>/data/clearndr-osd/runs/osd-import-<ts>/rc >/dev/null
  ```

  Запись `rc` финализирует прогон при следующем опросе статуса (работает и
  в старых сборках хаба); отредактированный так прогон считается
  остановленным, блокировка снимается.

## Если дашборды пустые или с ошибками (траблшутинг)

Типовые сообщения на панелях и их причины:

| Симптом | Причина | Что делать |
|---|---|---|
| `No results found`, «Всего событий: 0», при этом в `--check` данные есть | Пакеты смотрят на index-pattern, чей титул не покрывает индексы с данными: до v1.14.6 фолбэк «любой logstash*» выбирал, например, `logstash-smb-*` без smb-данных | Переимпортировать пакеты на v1.14.6+ (`--pack all`): паттерн выбирается по данным (титул = выражению индексов с `event_type`, поле времени обязано содержать значения), ссылки панелей переписываются на него |
| `Could not locate that index-pattern-field (id: dns.rrname)` и т.п. | В index-pattern урезанный/чужой список полей | На v1.14.6+ поля найденного паттерна объединяются (MERGE) с полным списком из кластера — свои записи SELKS сохраняются; переимпортировать пакеты и обновить страницу OSD (Ctrl+F5, кэш полей) |
| `Saved field "proto" is invalid for use with the "Terms" aggregation` | Поле text (динамический маппинг), Terms по нему невозможен | v1.14.5+ подставляет `proto.keyword` автоматически; переимпортировать пакеты |
| `Traceback … StopIteration` в секции «Полный список полей index-pattern», дальше «полей: 0» | Регрессия v1.14.5: в `_field_caps` есть поля-«объекты» (`dns`, `http`, `tls`, `flow`…) с единственным типом `object` — `osd_type` падал на пустом множестве типов | Исправлено в v1.14.6 — обновить скрипт и перезапустить |
| Панели по http-*/tls-*/fileinfo-* вырезаны (WARN «поля … вырезаны») | В кластере нет событий этих типов (индексов нет или пустые) — поле не появится из ниоткуда | Норма для набора протоколов этой установки: наполнение появится после того, как трафик породит соответствующие EVE-события; затем повторный `--pack all` |

Диагностика без изменений в кластере:

```bash
sudo /opt/ndr-rules-hub/scripts/clearndr-osd-dashboard-import.sh --check
```

Печатает: найденный источник EVE-данных (выражение индексов и число
документов с `event_type`), найденные поля (key → имя в кластере), все
index-pattern'ы (титул, поле времени, число полей в паттерне), число
документов и время последнего события. Код выхода 1 — EVE-данных нет.

Если `--check` показывает «документов нет»:

1. Проверить, пишется ли `eve.json` и читает ли его Logstash/Filebeat
   (`docker ps`, логи контейнера лог-пайплайна, `ss -ltnp | grep 9200`).
2. Посмотреть, в какой индекс реально падают события:
   `curl -k https://127.0.0.1:9200/_cat/indices?s=index&h=index,docs.count` —
   если это не `logstash-*`, укажите выражение индексов в `--check`/импорте
   или переименуйте паттерн: скрипт на v1.14.5+ сам переключается на индексы
   с `event_type`.
3. Если последнее событие старше 48 ч — расширить диапазон времени в OSD
   (скрипт предупреждает об этом в финальной проверке).
