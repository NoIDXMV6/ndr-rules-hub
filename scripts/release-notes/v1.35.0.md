Устранение блокировок БД и «зависаний» сборок; проверки индикаторов RST Cloud стали видимыми (v1.35.0).

Причина производственной проблемы (диагностика): сборка правил/DNS занимала ЕДИНСТВЕННУЮ коннекцию SQLite (connection_limit=1): интерактивные запросы (дашборд, опрос прогресса, логи) выстраивались в очередь на pool_timeout и падали «Socket timeout» — «система ушла в глубокий тайм-аут, чтение из БД замедлилось до неприемлемых показателей, диагностировать невозможно». Дополнительно: сборка правил грузила все 478 тыс. правил ОДНИМ запросом (include rules); сборка DNS держала 6 млн доменов в памяти и собирала файл одной строкой (~100 МБ) с блокирующей сортировкой — event loop стоял, опрос прогресса не отвечал, статус «непонятен», а в логах контейнера было пусто.

Два клиента БД (снятие блокировки чтения):
- src/lib/db.ts: `db` — интерактивный (API веб-интерфейса, auth, логи), `dbHeavy` — тяжёлый (сборки правил и DNS-списка, импорт SQL-дампа, загрузка источников, массовые createMany/deleteMany, потоковое чтение записей). У каждого своя коннекция (connection_limit=1) и свои PRAGMA (WAL, busy_timeout 15 с, synchronous NORMAL). В режиме WAL читатели не блокируют друг друга: пока сборка читает/пишет через свою коннекцию, интерфейс отвечает мгновенно.
- Тяжёлые операции переведены на dbHeavy: buildFinal (чтение правил, метаданные источников), fetchSourceById (диф + массовая замена правил), buildDomainList (чтение записей + запись результата), replaceDomainRecords, importDomainDump, userWorkspaceSources.

Разрядка event loop и память:
- buildFinal: правила читаются ПАКЕТНО по источникам (cursor-батчи по 20 тыс., touchBuild + yieldToLoop на каждом батче) вместо одного гигантского запроса; в журнале сборки — по-источниковый счёт правил.
- buildDomainList: файл списка доменов пишется СТРИМИНГОВО (writeDomainFileStreaming: порции по 20 тыс. строк → createWriteStream с await drain, sha256 инкрементально) — без массива из 6 млн строк и строки ~100 МБ; renderDomainFile сохранён (тесты/совместимость), шапка/строки выделены в domainExportHeaderLines/domainExportLine.
- Сортировка 6 млн доменов — sortStringsYielded (dns.ts): чанки по 100 тыс. сортируются отдельно, затем k-way слияние через min-кучу с yieldToLoop между порциями; порядок байт-в-байт совпадает с дефолтным Array.sort; mergeDomainSources разряжается каждые 200 тыс. записей.
- domainEntries (чтение записей источника): touchDnsBuild + yieldToLoop на каждом батче из 10 тыс.
- importDomainDump/replaceDomainRecords: yieldToLoop между чанками вставки/удаления.

Watchdog зависших сборок (статус всегда честный):
- build-progress.ts / dns-progress.ts: у задания есть признак жизни (touch на каждой стадии, строке журнала, батче); если активная сборка молчит дольше 10 минут (BUILD_STALE_MS/DNS_STALE_MS) — принудительное завершение с ошибкой «сборка прервана watchdog…» и записью в stdout: «вечная» активная сборка больше невозможна, очередь разблокируется, новый запуск можно выполнить сразу.
- Каждое событие сборки (стадии с процентом, журнал, финал/сбой с длительностью) дублируется в stdout контейнера: `docker logs` показывает ход сборки даже при недоступной БД/UI; в журнале сборки появились timings фаз (слияние X с, запись Y с, всего Z с).

Кэш тяжёлых счётчиков (COUNT больше не на каждый опрос):
- src/lib/engine/count-cache.ts: rulesCountCached/domainRecordsCountCached (TTL 60 с): свежее значение — мгновенно, устаревшее — отдаётся сразу и пересчитывается В ФОНЕ (дашборд никогда не ждёт COUNT); invalidateCounts() после массовых операций (загрузка источника, импорт дампа, замена записей источника, сборки).
- /api/dashboard (db.rule.aggregate на каждый опрос) и domainDashboard (db.domainRecord.aggregate) переведены на кэш.
- /api/dns/records: счётчик страницы БЕЗ точного COUNT(*) по 6 млн строк: без поиска — domainCount источника или кэш общего числа; с поиском — ограниченный перебор до 20 001 совпадения (raw SQL LIKE с ESCAPE, кэш 60 с), в ответе totalCapped, UI показывает «20000+»; выборка DomainOverride ограничена нужными полями.

Проверки RST Cloud — видны везде (по запросу «не вижу, где проверки»):
- Диалог проверки стал универсальным: поле ввода — любой индикатор (домен/IP/URL/хэш SHA-256), тип определяется API; открывается с готовым значением (записи DNS) или с пустым полем.
- Точки входа: карточка «RST Cloud — проверка индикаторов» во вкладке «Интеграции» (кнопка «Проверить индикатор»), кнопка «Проверить в RST Cloud» в тулбаре «Правил», кнопка у каждой записи в «DNS списки → Записи»; i18n ru/en, помощь обновлена.
- Сами проверки без изменений (v1.34.0): IoC Lookup (балл/теги/описание), Noise Control (доброкачественность/false positives), Whois; POST /api/rst/lookup и POST /api/rst/check; ключ — «Настройки → Токены источников → RST Cloud».
